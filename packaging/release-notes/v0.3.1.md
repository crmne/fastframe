fastframe 0.3.1 gives a Windows audio output the fixed buffer the app asked for. In 0.3.0 it got a 10 ms buffer, which brings back crackling under load.

Upgrade by moving the tag on every fastframe crate; nothing else changes:

```toml
fastframe-audio = { git = "https://github.com/crmne/fastframe", tag = "v0.3.1" }
```

## Fixed

- **A fixed audio buffer is the size the app asked for on Windows.** WASAPI in shared mode reports its 10 ms period as both ends of the buffer range, and 0.3.0 clamped a fixed size to that range. Spotifast's 100 ms buffer, which stops shared-mode underruns, therefore opened with 480 frames. The size is now asked for as given and clamped to the reported range only if the device refuses it, as CoreAudio does for sizes out of its range. On WASAPI, 100 ms now opens with 4800 frames and about 110 ms of latency. By @crmne. (crmne/spotifast#88)
- **The idle example measures more.** `cargo run -p fastframe-audio --example idle -- --buffer-ms 100` asks for a fixed buffer as Spotifast does. The example prints the largest callback and how soon the first callback follows `resume()`: within 2 ms on WASAPI and 7 ms on ALSA. By @crmne.

## Known limitations

- **macOS audio is untested.** A paused output gets no callbacks on ALSA, PulseAudio, PipeWire and WASAPI. On macOS the crate builds and passes its tests in CI, but nobody has played audio through it yet.
- **`release_after` takes effect only through `maintain()`**, as in 0.3.0.
