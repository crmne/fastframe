fastframe 0.13.1 fixes a noisy log in `fastframe-audio`. On PipeWire, listing audio devices or opening the default microphone no longer logs "Reactor error: Client disconnected" each time, and no longer starts a thread and a sound-server connection for every lookup.

Upgrade by moving every fastframe crate to the tag:

```toml
fastframe-audio = { git = "https://github.com/crmne/fastframe", tag = "v0.13.1" }
```

No code change is required.

## Fixed

- **Listing devices on PipeWire no longer fills the log with errors (`output_devices`, `input_devices`, `Input::open`, `device_id`).** cpal's PipeWire backend does not say which device its default stands for, so fastframe asks PipeWire's PulseAudio server. It made a new connection for every listing, every open of the default input and every default id lookup, and pulseaudio-rs logs `ERROR pulseaudio::client::reactor] Reactor error: Client disconnected` each time a connection closes, though nothing went wrong. ZapFast relists its devices every five seconds and logged it about 23 times a minute, 139 times over two calls. The process now keeps one connection for these lookups, shared by every thread that lists or opens devices and made again only after it fails, so a restarted sound server is still reached on the next lookup. It is never asked from an audio callback, and no lock is held while the server answers. Relisting every 100 ms for a minute while opening and closing the default input every second, on PipeWire 1.6.9 with a FLOW 8, logged 832 of these errors before and none after, and the process went through 378 threads before and 23 after. The audio itself was never affected. By @crmne.

## Known limitations

- **The connection's own thread stays for the life of the process.** One PulseAudio client named `cpal-pulseaudio-<pid>` appears in the server's client list from the first lookup on, where before one appeared briefly for each lookup.
- **pulseaudio-rs still logs the error when a connection closes.** fastframe now closes one only when it fails or the process exits, but an app that uses cpal's PulseAudio host directly still sees the line. That needs a fix in pulseaudio-rs itself. So does a system whose audio goes through cpal's PulseAudio host (PulseAudio without PipeWire): there every stream and listing still makes a connection of its own, as before.
- The Linux audio requirements and PipeWire default-input startup delay documented in [0.12.1](https://github.com/crmne/fastframe/releases/tag/v0.12.1) still apply. Only the first lookup of the process, or the first after the connection fails, now connects to the server; later ones reuse the connection.
